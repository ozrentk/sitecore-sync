# Languages and fallback

[Documentation index](README.md) · [Project overview](../README.md)

## Choose and lock languages

Use the language selector beside the connection in the tree toolbar. Browse has one selected language; Compare has an independent selector on each side, including when both sides use the same connection. A configured language does not guarantee that the selected item has a local version in it.

Enable **Lock Languages** to keep both sides on the same configured Sitecore language. If the current languages differ, choose which current language should be used on both sides. A language or connection change that cannot preserve the lock is blocked and offers an explicit unlock action; after unlocking for a connection change, the new side uses `en` when available or its first configured language. The lock never treats Sitecore language fallback or an item-level fallback version as proof that a language is configured.

## Switch languages without losing your place

Changing only comparison languages keeps the current tree visible while preparing a replacement in the background. A label centered at the top of each reloading side shows its target language, for example "Switching to en-CA...". Once the selected item, previously expanded branches, and their required details are ready, the view updates in one step, preserving selection and scroll position; collapsed branches stay collapsed. The unchanged comparison side reuses its loaded data. Field Diff follows the committed selection. Tree transfer, publishing, and editing actions are unavailable during preparation, while scrolling, language choices, and item selection remain available. A failed load retains the previous view and offers Retry; choosing its displayed language restores it immediately. New language choices supersede pending preparation, and favorite or site navigation takes precedence. If an item no longer exists, the prepared view selects its nearest available ancestor with an explanation. Connection changes retain the full reset behavior.

## Compare exact and effective values

New content tabs start in **Exact locale**. Enable **Fallback** in either the tree comparison or Field Diff toolbar to compare Sitecore-provided effective field values independently on each side. The mode stays selected while navigating, and switching it preserves tree expansion and selection. The tree and details Fallback toggles stay synchronized; turn Fallback off for Exact locale. **Lock Languages** is also a toggle button in the tree toolbar. Fallback fields show **fallback · expected source: en** (using the candidate locale) when that side has a suitable configured item-fallback candidate. The tooltip explains that this is a configured candidate, not verified per-field provenance, and shows the chain. Otherwise they retain **source language unknown**. Matching text never establishes provenance; the hint does not affect comparisons, transfers or publishing. Field-transfer arrows are available only in Exact locale. In Browse, Fallback sits immediately to the right of the language selector and is also available in Item Details; publishing remains exact-locale, and tree transfers still include all languages and versions. Closing the comparison tab resets the mode for the next tab.

When a requested locale has version 0, Fallback displays the effective fields returned by Authoring without replacing its language/version metadata. Item Details shows a **configured fallback candidate** when a bounded traversal of language definitions finds a version and the item's shared Enable Item Fallback flag is enabled (including Standard Values). The candidate chain is configuration evidence, not confirmed whole-item or per-field provenance. Values always come from the original-locale server response; candidate content is never substituted. Missing/invalid metadata, cycles, failed reads or traversal limits leave the source unverified. Language-definition metadata is read in `en`; environments without readable English metadata remain unverified. Exact locale stays the default. These reads do not change or publish content.

## Collect a read-only fallback diagnostic

To collect evidence without enabling the browser Playground, run **XM Cloud Sync: Collect Authoring Fallback Diagnostic** from the Command Palette. Choose a saved connection and **Schema only**, or **Item probes and fallback configuration**. For item probes, paste the item GUID and enter comma-separated locales: requested locale first, then up to seven candidates (for example `en-NZ, en-AU, en`). The command uses the existing Authoring client and stored credentials; it does not modify items or configuration.

The report opens as an unsaved JSON document. Save it locally if needed and review its selected item content before sharing. Known authentication credentials are redacted; unrelated secrets stored in content cannot be identified automatically. Reports are not uploaded, logged or saved automatically. A failed schema read does not prevent item probes. Each probe follows up to 50 pages, with a 6 MiB total evidence budget and explicit incomplete/error statuses. Cancel stops collection without opening a partial report. Exact candidate reads precede a fallback-enabled read of the original locale; these are independent observations, not a transactional snapshot or a verified chain.

The investigation in [the fallback research report](research/fallback-spike.md) records the remaining configuration/provenance questions. From a source checkout's root, the offline helper `node --import tsx scripts/fallback-spike.ts` generates queries and validates exported schemas without network requests; it is not part of the installed VSIX. The diagnostic tools do not change content or fallback configuration. Verified source resolution remains deferred.

The item option also collects language definition items and follows their observed fallback-language GUID or validated locale-name references, reads selected content-field definitions in the supplied locales, and follows the selected item template’s base-template and Standard Values references. Configuration reads always disable fallback. Fields already marked as fallback take priority; up to 16 field definitions, 16 language items, 16 template/Standard Values items and 96 configuration item reads are collected. The same evidence-byte budget applies, and coverage reports all selection/traversal limits. The configuration section retains fallback/scope/reference settings rather than unrelated definition fields. Environment/context enablement and the per-language field-settings switch remain unknown unless separately verified. Missing settings never mean disabled.

Reports use `formatVersion: 3`. Every non-null outer item must match its requested identity and exact locale (case-insensitive); legitimate fallback values inside fields remain valid. A version-0 item with `fields: null` is still recorded as a completed observation with `outcome: "no-local-fields"`, preserving the null response. It is not an API failure or proof that fallback cannot apply.

The original-locale cross-check is labeled **field-fallback read (item.fields only)**. `withLanguageFallback` affects only that field collection; each page exposes the outer returned item ID, language and numbered version separately. This does not establish whole-item substitution or the source locale of a field.

If the outer numbered version changes between pages, the affected probe restarts once from page one, with version omitted to request latest again. `discardedAttempts` retain the old pages separately and `restarts` records the restart. No pages from the old attempt enter the new result or configuration discovery. Repeated drift reports `item-changed` rather than complete. Stable numbered versions still do not guarantee a transactional snapshot: edits within the same version can happen between reads.

Pages and probes reference `requests`, which link to the actual fixed query text in `queries` and retain the sent variables, locale, cursor and omitted/latest version choice. Each diagnostic GraphQL request records start/end time and up to four HTTP attempts with timing, status, safe failure category and scheduled retry delay. HTTP attempt timing ends at response headers; request timing includes parsing. Headers, cookies, credentials and raw error messages are excluded. Backend identification/affinity remains deferred in B30; routing is unchanged. Collection shares a 50-page request limit per probe across both attempts, a report-wide limit of 512 GraphQL requests, and a 6 MiB budget for evidence entries (before pretty-printing), including query/request traces and discarded pages. Coverage reports exhausted budgets and any omitted trace. To compare successive reports, use the same item and locales as the previous run; no extra configuration inputs are needed.

## Create controlled fallback test items

Run **XM Cloud Sync: Create Fallback Test Items** in the Command Palette. Choose the development connection, a content parent ID, a representative existing page or component ID, and the requested-to-source locale list (for example `en-NZ, en-AU, en`). Choose a versioned text field from the representative item. The command reads its template and creates four uniquely named children beneath the chosen parent after showing a confirmation with the parent, template and field:

- Source-only version in the last locale, with item fallback enabled.
- Source-only version in the last locale, with item fallback disabled.
- Requested-locale version with a local marker.
- Requested-locale version with an empty field value.

Only the selected field and item fallback checkbox are supplied; other fields retain template defaults. This is a template-based test item, not a clone of the representative page or its datasource tree. Field fallback settings, language definitions and templates stay unchanged. The disabled control disables **item** fallback only; field fallback can still apply. Empty controls have no source-language version, so they do not settle empty-versus-reset behavior against a populated candidate. For additional isolated scope fixtures, see [MCP fixture tools](mcp.md#isolated-scope-fixtures). Environment switches still require separate evidence.

Run the creation command separately with a page and component representative to compare both cases. Nothing is published, deleted or automatically retried. Test runs, generated values and intended paths are stored in VS Code workspace state before mutations, and a JSON report opens on completion or failure. A failed creation may have succeeded remotely, including when its follow-up read failed: inspect the recorded path for `outcome-unknown` entries before creating another set. Runs are never replayed automatically. Existing items are not edited.

Next run **XM Cloud Sync: Diagnose Fallback Test Items**, choose the recorded run, and share the resulting JSON after reviewing it. The command uses that run's saved connection, locales and confirmed item IDs, collecting the same exact/configuration/fallback cross-check evidence for each item. It refuses a changed server URL. Interrupted diagnostic reports retain collected observations; unconfirmed creations are excluded. Reports do not assert resolved sources or snapshot consistency. Keep the test items for further inspection; there is no automatic cleanup command.

Fallback test creation and diagnostic GUID/locale textboxes stay open when focus moves to another window, allowing IDs to be copied and pasted. Press Escape to cancel.
